# STM32CubeMX and STM32CubeIDE Setup Guide
## Gravimetra AGD-250 Controller - Expanded First-Time-User Edition

**Target microcontroller:** STM32G491RET6, LQFP64  
**Configuration tool:** Standalone STM32CubeMX 6.18.1 or a later compatible STM32CubeMX 6.18.x maintenance release  
**Build/debug tool:** Eclipse-based STM32CubeIDE 2.2.0 or a later compatible 2.x release  
**Project name used in this guide:** `Gravimetra_AGD250_Controller`  
**Document revision:** 2.1 - expanded, electrically corrected, and current through 2026-08-15  
**Primary purpose:** Create the authoritative `.ioc` hardware-configuration project, generate a buildable STM32CubeIDE project, import it into STM32CubeIDE, and understand every setting selected for the Gravimetra AGD-250 controller.

**Audience:** A person who is comfortable with electronics and PCB design but has never created an STM32CubeMX project or used STM32CubeIDE.

**Scope:** This document takes you from installing the tools through generating, importing, building, and debugging the initial MCU project. It configures the MCU, pins, clocks, peripherals, interrupts, middleware, and safe startup states. It does **not** implement the complete scale, TMC2209, Nextion, ADS1262, calibration, or dispensing firmware; it creates the hardware-abstraction foundation those drivers will use.

## Important reading rule

Work through the guide in order. Do not enable every peripheral first and attempt to repair conflicts afterward. Save the `.ioc` file after every major section. When this guide calls a value a **starting value**, enter it exactly for the first build, then change it later only after measurement or a documented design decision.

> **CubeMX is not an electrical-design checker.** It can detect many conflicts inside the MCU, but it cannot verify your external regulator, decoupling capacitors, pull resistors, USB-C CC resistors, CAN/RS-485 transceivers, E-stop chain, TMC2209 socket wiring, analog reference, or reset-time safety. Those remain schematic and PCB responsibilities.

> **Revision-A safety principle:** Software may supervise motion, but it must not be the only means of stopping it. The physical E-stop must remove or inhibit motor/calibration/robotic motion independently of MCU execution. The MCU, Nextion, scale electronics, and communication interfaces may remain powered so the fault can be displayed and logged.

## Corrections incorporated in this revision

This revision intentionally supersedes the earlier CubeMX guide. Important corrections include:

- LQFP64 analog supply pins are **27 = VSSA, 28 = VREF+, 29 = VDDA**.
- `TMC4_EN_N` is on **PB9**, not PB4.
- PB4 is reserved because it has JTRST/reset and UCPD dead-battery behavior.
- ADS1262 SPI starts at **170 MHz / 64 = 2.65625 MHz** rather than approximately 5.3 MHz.
- I2C3 starts at **100 kHz**, not 400 kHz, because it crosses the board-to-board environment and carries only low-rate sensors/power-management traffic.
- PC3/ADC1 uses a long **640.5-cycle** sampling time for a high-impedance battery-divider source.
- The guide explicitly disables the STM32G4 UCPD dead-battery pull-down behavior early in startup because PB6 is used for the Nextion UART.
- STM32CubeIDE 2.x is treated correctly as a separate coding/debug tool; the `.ioc` file is edited in standalone STM32CubeMX.
- The generated project remains C at its boundary while application logic may be added as C++ without renaming CubeMX-generated files.

# 1. What CubeMX and CubeIDE each do

This distinction is important because this guide deliberately uses two separate tools: standalone STM32CubeMX for hardware configuration/code generation and STM32CubeIDE for compiling, programming, and debugging. That separation makes the authoritative `.ioc` workflow explicit and matches ST's documented generated-project workflow.

## 1.1 STM32CubeMX

STM32CubeMX is the graphical **microcontroller configuration and code-generation tool**.

Use CubeMX to:

- select the exact STM32 part number and package,
- choose which function appears on each physical MCU pin,
- configure oscillators and the clock tree,
- configure UART, SPI, I2C, timers, ADC, USB, CAN, CRC, GPIO, interrupts, and middleware,
- detect many pin and clock conflicts,
- save the configuration in an `.ioc` file,
- generate initialization source code and project files for STM32CubeIDE.

CubeMX does **not** compile your program, flash the MCU, or provide the normal source-level debugger.

## 1.2 STM32CubeIDE

STM32CubeIDE is the **code editor, compiler, linker, programmer, and debugger**.

Use CubeIDE to:

- open the project generated by CubeMX,
- write the application firmware,
- compile and link it,
- program the MCU through ST-LINK,
- set breakpoints,
- inspect variables and peripheral registers,
- single-step through code,
- view build errors and warnings.

For this project, do not depend on an embedded pinout editor inside CubeIDE. Open and edit the `.ioc` file in standalone STM32CubeMX, regenerate the STM32CubeIDE project, and then refresh/rebuild it in CubeIDE. Some tool installations may expose additional integration, but the standalone-CubeMX workflow is explicit, reproducible, and supported by ST.

## 1.3 The normal workflow

```text
Standalone STM32CubeMX
    |
    | configure pins, clocks, peripherals, middleware
    | save .ioc
    | Generate Code
    v
Generated STM32CubeIDE project
    |
    | import into STM32CubeIDE
    | compile, program, debug, write firmware
    v
Custom STM32G491 controller PCB
```

When you later need to change a pin or peripheral:

```text
1. Stop the CubeIDE debug session.
2. Save your source files.
3. Open the .ioc in standalone CubeMX.
4. Make the hardware-configuration change.
5. Generate Code again.
6. Return to CubeIDE.
7. Press F5 or use File -> Refresh.
8. Rebuild and review the source-control diff.
```

## 1.4 Vocabulary used throughout this guide

| Term | Meaning in this project |
|---|---|
| MCU | The STM32G491 microcontroller itself |
| Peripheral | A hardware block inside the MCU, such as SPI1, USART1, TIM2, ADC1, or FDCAN2 |
| Alternate function | A non-GPIO function connected to a physical pin, such as `PA5 = SPI1_SCK` |
| GPIO | A pin used directly as a digital input or output rather than by a peripheral |
| `.ioc` | CubeMX project/configuration file; the authoritative machine-readable record of selected pins, clocks, middleware, and generation options |
| HAL | ST's Hardware Abstraction Layer driver library; the baseline driver layer selected in this guide |
| LL | ST's lower-level driver layer; more direct but not selected initially |
| CMSIS | Arm/ST device definitions, core support, startup declarations, and register definitions used by the generated project |
| Middleware | Software above the basic drivers, such as the USB Device stack |
| NVIC | Nested Vectored Interrupt Controller; prioritizes peripheral and GPIO interrupts |
| EXTI | External interrupt/event controller used for GPIO-edge interrupts such as ADS1262 DRDY |
| DMA | Direct Memory Access; moves data between a peripheral and memory without a CPU copy for each byte |
| Clock tree | The network of oscillators, PLLs, dividers, and bus clocks that sets MCU/peripheral speed |
| Toolchain | Compiler, assembler, linker, and related build tools; CubeIDE supplies the Arm GNU toolchain for this workflow |
| Build | Compile source files and link them into an executable firmware image |
| Flash/program | Write the firmware image into MCU nonvolatile memory |
| Debug | Run under ST-LINK control so execution can stop at breakpoints and internal state can be inspected |
| Workspace | CubeIDE's local IDE-state directory; it is not the same thing as the firmware project directory |

# 2. Why this project uses STM32G491RET6

The design uses many simultaneous communication interfaces:

- one UART for the Nextion display,
- four independent single-wire UARTs for four TMC2209 modules,
- one UART for RS-485,
- SPI for the ADS1262 precision ADC,
- I2C for TMP117 sensors and power-management devices,
- USB device support,
- FDCAN for future machine and robotic-arm communication,
- four hardware timer outputs for step pulses,
- several safety and calibration GPIOs.

The STM32G491 provides:

- three USART peripherals,
- two UART peripherals,
- one low-power UART,
- two FDCAN controllers,
- USB Full Speed device hardware,
- three SPI peripherals,
- three I2C peripherals,
- many timers,
- 512 KB of flash in the selected `E` memory size,
- a 170 MHz Cortex-M4F CPU,
- an LQFP64 package that is practical for normal PCB assembly.

The exact ordering code is:

```text
STM32G491RET6
```

For this guide, the most important parts of that code are:

- `G491`: MCU family and feature set,
- `R`: 64-pin device class,
- `E`: 512 KB flash-memory version,
- `T`: LQFP package,
- `6`: the selected commercial temperature-grade suffix.

Do not accidentally select a similarly named G491 part with a different package or memory size. A different package can have a different set of available pins even when the core MCU family is the same.

# 4. Install and verify the STM32 tools

STM32CubeMX and STM32CubeIDE are separate programs in the current 2.x workflow. Install both. CubeMX creates and regenerates the project; CubeIDE compiles, programs, and debugs it.

## 4.1 Download the correct applications

As of 2026-08-15, STM32CubeMX 6.18.1 is the current 6.18 maintenance release and STM32CubeIDE 2.2.0 is the current Eclipse-based IDE release used by this guide. ST publishes the 6.18.0 online manual for the 6.18 generation; minor maintenance releases can retain that manual version number. If ST has issued a newer compatible maintenance build when you begin, record the exact version and review its release notes before allowing it to migrate the project.

From STMicroelectronics, obtain:

1. **STM32CubeMX** - use the normal STM32CubeMX application for STM32G4/HAL1 devices. Do not select STM32CubeMX2 for this project.
2. **STM32CubeIDE** - use the Eclipse-based STM32CubeIDE. This guide was written around the 2.2.0 user interface.
3. **STM32CubeProgrammer** - optional for normal builds but strongly recommended for device recovery, option-byte inspection, mass erase, and independent ST-LINK tests.

The applications are free, but ST may require accepting its license and may require an ST account for the installer download.

## 4.2 Install on Windows

1. Close other STM32 tools before starting the installers.
2. Run each installer as an administrator if Windows blocks driver installation.
3. Keep the default program locations unless you have a controlled tools directory.
4. Allow installation of ST-LINK USB drivers when prompted.
5. Reboot if the installer requests it.
6. Launch STM32CubeMX once and then close it.
7. Launch STM32CubeIDE once and choose a temporary workspace; this verifies that Java/Eclipse components start correctly.
8. Connect an ST-LINK and verify that Windows Device Manager does not show an unknown USB device.

## 4.3 Install on Ubuntu 24.04 or another supported Linux distribution

1. Download the Linux installers from ST.
2. Extract the installer archive if required.
3. Mark the installer executable, for example:

   ```bash
   chmod +x SetupSTM32CubeMX-*.linux
   chmod +x st-stm32cubeide_*.sh
   chmod +x SetupSTM32CubeProgrammer-*.linux
   ```

4. Run the installers using the method described by the included ST installation notes. A typical installation is either per-user or under `/opt/st/`.
5. Allow the installer to install ST-LINK udev rules. These rules permit a normal user to access the USB debugger without running CubeIDE as root.
6. Log out and back in after udev-rule installation, or reboot.
7. Connect the ST-LINK and run:

   ```bash
   lsusb
   ```

   Confirm that an STMicroelectronics/ST-LINK device appears.
8. **Do not run CubeIDE as root.** Root-owned workspace and build files cause persistent permission problems.

If CubeIDE cannot see ST-LINK but `lsusb` can, check that the ST udev rules were installed and reloaded. Do not solve the problem by permanently granting world-write access to USB devices.

## 4.4 First launch of standalone STM32CubeMX

1. Launch **STM32CubeMX**.
2. Open:

   ```text
   Help -> Check for Updates
   ```

3. Install a normal maintenance update if the installed build is older than the version intended for this project.
4. Restart CubeMX after an update.
5. Open:

   ```text
   Help -> About
   ```

6. Record the exact CubeMX version in a text file or project README.

Why record it: a later CubeMX version can regenerate initialization code differently or migrate the `.ioc` schema. Tool upgrades should be reviewed, not performed casually during board bring-up.

## 4.5 Install the STM32CubeG4 firmware package

CubeMX itself contains the graphical device database, but code generation depends on the **STM32CubeG4 MCU package**. That package contains the STM32G4 CMSIS device files, startup code, HAL drivers, USB middleware integration, and examples.

In CubeMX:

1. Open:

   ```text
   Help -> Manage embedded software packages
   ```

2. Expand **STM32Cube MCU Packages**.
3. Locate **STM32CubeG4**.
4. Select the current stable package supported by your CubeMX installation.
5. Click **Install Now**.
6. Wait for download and extraction to finish.
7. Verify that the version is marked **Installed**.
8. Record the package version. For example, record it as `STM32CubeG4 vX.Y.Z`; use the actual installed value rather than copying a value from this guide.

Why pin the package version after first success: the package determines the generated HAL APIs, startup file, middleware, and device headers. A package upgrade can change both source and behavior.

## 4.6 First launch of STM32CubeIDE

1. Launch **STM32CubeIDE**.
2. When asked for a workspace, choose a dedicated workspace directory such as:

   ```text
   C:\STM32_Workspaces\Gravimetra
   ```

   or:

   ```text
   ~/STM32_Workspaces/Gravimetra
   ```

3. Do not choose the firmware source directory as the workspace.
4. Allow CubeIDE to finish its first-start indexing and tool discovery.
5. Open:

   ```text
   Help -> About STM32CubeIDE
   ```

6. Record the exact IDE version.
7. Close CubeIDE until the CubeMX project has been generated.

### Workspace versus project

- The **project directory** contains the source code and belongs in version control.
- The **workspace** contains Eclipse metadata, window state, indexes, and local launch information.
- One workspace can contain several projects.
- The workspace `.metadata` directory should not be committed to Git.

## 4.7 Install and test STM32CubeProgrammer

CubeProgrammer is useful even though CubeIDE can program the MCU.

Use it later to:

- confirm that ST-LINK can identify the device,
- perform a full chip erase,
- inspect or change option bytes,
- recover a board that immediately enters low-power mode or reconfigures SWD pins,
- verify flash contents independently of CubeIDE.

Do not change option bytes merely to experiment. Save a screenshot/export of original option-byte values before changing them.

Before creating the project, confirm:

# 6. Understand the MCU pins CubeMX cannot design for you

Before assigning peripherals, understand which connections exist physically but do not appear as ordinary configurable signals in CubeMX. These are schematic obligations.

## 6.1 Power, reset, and reference pins

For the STM32G491RET6 LQFP64 package:

| Physical pin | Pin name | Required schematic treatment |
|---:|---|---|
| 1 | VBAT | Connect to 3.3 V when no separate RTC/backup battery is used. Do not leave it floating. Add the decoupling recommended by ST if the backup domain is used. |
| 7 | PG10-NRST | Dedicated active-low reset. Route to the SWD connector, reset pushbutton/test point, and the reset network. Do not treat it as a normal application GPIO. |
| 15, 32, 47, 63 | VSS | Digital ground. Connect all four to the continuous ground system with short, low-inductance paths. |
| 16, 33, 48, 64 | VDD | 3.3 V digital supply. Each VDD/VSS neighborhood needs local ceramic decoupling close to the pins. |
| 27 | VSSA | Analog ground. Connect to the quiet ground region without forcing motor, regulator, or display current through the local return path. |
| 28 | VREF+ | Positive ADC reference input. For Revision A it is supplied from the selected clean analog/reference network. It must never exceed VDDA or the device limit. |
| 29 | VDDA | Analog supply for ADC/analog resources. Decouple locally and follow ST's VDDA/VREF filtering guidance. |

The order of pins 27-29 is easy to transpose. Verify it in both the STM32 datasheet package diagram and the Altium symbol:

```text
Pin 27 = VSSA
Pin 28 = VREF+
Pin 29 = VDDA
```

## 6.2 Decoupling is not created by CubeMX

CubeMX can generate clock and peripheral initialization, but it cannot place capacitors. In the Altium schematic and PCB:

- place a local ceramic capacitor at every VDD/VSS pair,
- add the bulk capacitance recommended by ST near the MCU supply region,
- decouple VDDA and VREF+ according to the analog-supply design,
- keep high-current TMC2209, display, charger, and motor returns away from the VREF+/VDDA neighborhood,
- connect the exposed power system exactly as shown by the latest STM32G491 datasheet and AN5093 hardware-development note.

Do not copy a decoupling network from an unrelated STM32 family without comparing the current G491 documentation.

## 6.3 SWD programming connector

Provide at least these signals on the controller PCB:

```text
SWDIO  = PA13
SWCLK  = PA14
NRST   = PG10-NRST
GND
VTREF  = target 3.3 V reference
```

Optional but useful:

- SWO if a spare compatible pin exists in a later revision,
- 5 V only when the board intentionally supports debugger-supplied power,
- a keyed 10-pin Cortex debug connector or a compact Tag-Connect footprint.

The ST-LINK `VTREF` connection senses the target voltage; it is not permission to power the complete motors/display/scale through the debugger.

## 6.4 BOOT0

PB8 is also the BOOT0-capable pin for this package. Provide:

- an external pull-down,
- an accessible test pad or service jumper if system-memory boot access is desired,
- no permanent application load that can force it high during reset.

CubeMX runtime pull settings do not replace the reset-time external strap.

## 6.5 Reset-time behavior exists before `MX_GPIO_Init()`

At reset, GPIO pins are not yet in the output states selected later in CubeMX. Therefore hardware must make the safe state independent of firmware:

- external pull-ups keep every `TMCx_EN_N` high/disabled,
- an external pull-down keeps `GLOBAL_MOTION_ENABLE` low,
- an external pull-down keeps `RS485_DE` low/receive,
- the analog-servo clamp/reset circuit defaults to its safe state,
- the calibration actuator defaults off,
- the E-stop interrupts the motion-enable path in hardware.

CubeMX's initial GPIO output level only takes effect when generated firmware runs `MX_GPIO_Init()`.

## 6.6 USB-C hardware is not a CubeMX setting

CubeMX configures PA11/PA12 and the USB device stack. The PCB still needs:

- USB-C receptacle,
- CC1 and CC2 sink pull-down resistors appropriate for a USB device,
- USB D+/D- ESD protection,
- controlled and short differential routing,
- VBUS detection/divider network to PA9,
- prevention of USB VBUS back-powering the self-powered machine.

## 6.7 CAN and RS-485 require external transceivers

The STM32 contains:

- an FDCAN protocol controller,
- UART/LPUART peripherals.

It does **not** contain:

- a CANH/CANL physical transceiver,
- an RS-485 A/B physical transceiver.

The controller PCB therefore uses the selected TCAN1042-family CAN transceiver and THVD1450-family RS-485 transceiver, plus termination, protection, and connectors.

# 7. Configure the system core before assigning application peripherals

System-core settings reserve the debugger and oscillator pins and establish behavior used by all other peripherals. Configure them first so CubeMX does not assign those pins elsewhere.

## 7.1 Configure SYS for Serial Wire Debug

In the left tree, open:

```text
Pinout & Configuration -> System Core -> SYS
```

Under **Mode**, set:

| Setting | Select | Why |
|---|---|---|
| Debug | `Serial Wire` | Reserves PA13/SWDIO and PA14/SWCLK while leaving PA15, PB3, and PB4 available or reservable for the application. |
| System Wake-Up pins | Disabled | No wake-from-standby input has been defined for Revision A. |
| Timebase Source | `SysTick` | Supplies the HAL millisecond tick in the initial non-RTOS project. |

### Why not JTAG

Full JTAG normally consumes additional pins including PA15, PB3, and PB4. This design needs PA15 for `TMC2_EN_N`, PB3 for `AUGER4_DIR`, and intentionally reserves PB4. Serial Wire provides normal programming, breakpoints, memory/register inspection, and reset control using fewer pins.

### Why not asynchronous trace/SWO now

Trace would consume another pin and is not required to prove first hardware. Standard SWD debugging and USB/UART logging are sufficient for Revision A. Trace can be reconsidered only after the pin map is deliberately revised.

### Why SysTick now

The project initially has no RTOS. SysTick is the simplest HAL timebase and supports `HAL_GetTick()` and timeout handling. If FreeRTOS is introduced later, move the HAL timebase to another timer if required by that RTOS integration.

## 7.2 Configure RCC oscillator ownership

Open:

```text
Pinout & Configuration -> System Core -> RCC
```

Set:

| RCC field | Value | Why |
|---|---|---|
| High Speed Clock (HSE) | `Disable` | Revision A uses HSI16 and keeps PF0/PF1 for application signals. |
| Low Speed Clock (LSE) | `Disable` | No precision battery-backed RTC is required initially; PC14/PC15 remain reserved. |

### HSE design caveat

Using HSI16 minimizes parts and makes first bring-up easier. It is adequate for the CPU and ordinary local serial peripherals. FDCAN, however, is sensitive to oscillator tolerance. Treat the HSI-based 500 kbit/s CAN setup as a bench/short-bus baseline. Before calling CAN production-qualified over a long or harsh network, either:

- demonstrate adequate timing margin over voltage and temperature, or
- revise the hardware/pin map for a suitable external HSE source.

Do not populate an HSE crystal while PF0/PF1 are still wired as application signals.

### LSE reservation

PC14 and PC15 remain unused in the baseline. Keeping them free preserves the option of adding a 32.768 kHz LSE crystal for a precise RTC in a later revision.

## 7.3 Configure PWR defaults

Open:

```text
Pinout & Configuration -> System Core -> PWR
```

Do not enable low-power modes, programmable voltage detector interrupts, or UCPD/USB Power Delivery middleware for the first project.

The 170 MHz clock requires the appropriate high-performance voltage-scaling/boost setting. CubeMX normally inserts that setting as part of `SystemClock_Config()`. You do not need to create a separate application feature for it, but you must verify the generated clock function after code generation.

## 7.4 Reserve PB8 as BOOT0

In the package view:

1. Click **PB8**.
2. Select `GPIO_Input`.
3. Set the user label to:

   ```text
   BOOT0_RESERVED
   ```

4. In the GPIO settings, use **No pull** because the schematic provides the authoritative external pull-down.
5. Do not connect PB8 to a normal application connector.

Why configure it as a digital input rather than leaving it analog/unassigned: ST recommends putting an otherwise unused PB8 into a defined non-analog mode after startup to limit unnecessary consumption. The external resistor still controls the reset-time boot state.

## 7.5 Reserve PB4 and understand the UCPD dead-battery pull-downs

Configure PB4 as a harmless input:

1. Click **PB4**.
2. Select `GPIO_Input`.
3. Label it:

   ```text
   UCPD_PB4_RESERVED
   ```

4. Select **No pull**.
5. Do not route it to a critical enable or direction signal.

The STM32G491 contains UCPD dead-battery support. After reset, an internal approximately 5.1 kohm pull-down can be activated on:

- PB6 (`UCPD1_CC1`) when PA9 (`UCPD1_DBCC1`) is high,
- PB4 (`UCPD1_CC2`) when PA10 (`UCPD1_DBCC2`) is high.

This project uses:

- PB6 as `NEXTION_TX`,
- PA9 as `USB_VBUS_SENSE`,
- PA10 as `AUGER2_DIR`.

A connected USB host can make PA9 high. Without disabling dead-battery support, PB6 can therefore be loaded by the internal 5.1 kohm pull-down. That is undesirable on the Nextion transmit signal.

### Required early-startup action

Set `PWR_CR3.UCPD1_DBDIS = 1` before normal GPIO/peripheral use.

After code generation, put the operation in CubeMX's preserved **SysInit** user section, after `HAL_Init()` and before `MX_GPIO_Init()`. A robust register-level form is conceptually:

```c
/* USER CODE BEGIN SysInit */
__HAL_RCC_PWR_CLK_ENABLE();
SET_BIT(PWR->CR3, PWR_CR3_UCPD1_DBDIS);
/* USER CODE END SysInit */
```

The exact HAL convenience-function name can vary with the installed STM32CubeG4 package. Search the generated package header `stm32g4xx_hal_pwr_ex.h` for `DeadBattery`, `UCPD`, or `DBDIS`. Use the available official function if present; otherwise the register operation above is explicit and easy to audit.

Why this must be early: the setting removes the UCPD dead-battery pull-down effect before PB6 begins normal UART operation. Firmware cannot change the electrical state that exists while the MCU is completely unpowered, which is another reason PB4 is not used as a critical output.

- PF0/PF1 are available for application GPIO,

# 8. Configure the 170 MHz clock tree

## 8.1 Clock terminology

The important clock terms are:

- **HSI16:** internal 16 MHz RC oscillator.
- **PLL:** phase-locked loop that multiplies/divides an input clock.
- **SYSCLK:** selected top-level system clock.
- **HCLK:** CPU/AHB bus clock after the AHB prescaler.
- **PCLK1/PCLK2:** APB peripheral bus clocks.
- **HSI48:** internal 48 MHz oscillator used for USB.
- **CRS:** Clock Recovery System used to trim HSI48 from USB Start-of-Frame timing.

The system-clock calculation is:

```text
PLL input = HSI16 / PLLM
          = 16 MHz / 4
          = 4 MHz

PLL VCO = PLL input * PLLN
        = 4 MHz * 85
        = 340 MHz

PLL R output = PLL VCO / PLLR
             = 340 MHz / 2
             = 170 MHz
```

## 8.2 Enter the clock settings

Open the **Clock Configuration** tab.

Set or verify:

| Clock-tree field | Value |
|---|---:|
| PLL source | HSI16 |
| PLLM | /4 |
| PLLN | x85 |
| PLLR | /2 |
| PLL R output enabled | Yes |
| System Clock Mux | PLLCLK |
| AHB prescaler | /1 |
| APB1 prescaler | /1 |
| APB2 prescaler | /1 |
| SYSCLK | 170 MHz |
| HCLK | 170 MHz |
| PCLK1 | 170 MHz |
| PCLK2 | 170 MHz |

Do not type 170 MHz into every output box blindly. Select the source and divider values and allow CubeMX to calculate the downstream clocks.

### Why use 170 MHz

- It is the rated maximum CPU frequency for the device.
- It gives ample processing margin for filtering, temperature compensation, HMI parsing, USB logging, and communication protocols.
- It makes the proposed timer prescaler produce a convenient 1 MHz step-timer tick.

### Voltage scaling and boost mode

The STM32G491 requires the appropriate internal voltage-regulator performance mode for 170 MHz.

CubeMX should generate the required power configuration automatically. After code generation, verify that `SystemClock_Config()` includes the appropriate voltage-scaling/boost call before switching to 170 MHz. Do not manually remove it.

### Flash latency

At 170 MHz, flash-memory wait states are required. CubeMX calculates and generates the flash latency. Do not manually select a lower latency to make the clock page look simpler; incorrect latency can cause unpredictable execution faults.

## 8.3 Configure the USB clock

In the clock tree:

1. Enable **HSI48**.
2. Select **HSI48** as the USB clock source.
3. Verify the USB clock shows exactly **48 MHz**.

USB Full Speed requires a tightly controlled 48 MHz clock. The internal HSI48 oscillator is intended for this use when paired with the Clock Recovery System.

## 8.4 Configure CRS

After HSI48 and USB are enabled, open:

```text
Pinout & Configuration -> System Core -> CRS
```

Enable CRS and set:

| CRS setting | Value |
|---|---|
| Synchronization source | USB SOF |
| Synchronization divider | 1 |
| Synchronization polarity | Rising edge |
| Automatic trimming | Enabled/default behavior |
| Reload and error-limit values | CubeMX calculated defaults |

### Why use USB SOF

A connected USB host sends a Start-of-Frame event every millisecond. CRS measures HSI48 against that timing and automatically trims the oscillator.

This synchronization source is internal to the USB peripheral; it does not consume PA10 even though PA10 has an unrelated `USB_CRS_SYNC` alternate function for external synchronization.

CRS cannot synchronize from USB SOF before the host is connected and producing frames. The initial HSI48 trim allows enumeration to begin, after which CRS improves the clock accuracy.

## 8.5 Configure the FDCAN kernel clock

In the peripheral-clock section of the clock page, select:

```text
FDCAN clock source = PCLK1
```

The resulting FDCAN kernel clock should be 170 MHz.

The CAN bit-timing values later in this guide assume 170 MHz. If you change the FDCAN source or system clock, the CAN prescaler and time segments must be recalculated.

## 8.6 Configure the ADC1 kernel clock

In the peripheral-clock selection area, set:

```text
ADC12 clock source/prescaler = Synchronous clock mode, HCLK / 4
```

With HCLK at 170 MHz:

```text
ADC clock = 170 MHz / 4 = 42.5 MHz
```

Why: the STM32G491 ADC clock must remain within its allowed operating limit. 42.5 MHz gives ample speed for the occasional battery/system-voltage sample and avoids operating near the maximum. The precision scale measurement does not use ADC1; it uses the external ADS1262.

If CubeMX presents this setting inside **ADC1 -> Parameter Settings** instead of the clock page, select the same synchronous HCLK/4 value there.

## 8.7 Clock-page acceptance checks

Before leaving the clock page:

- no field is red or magenta,
- SYSCLK = 170 MHz,
- HCLK = 170 MHz,
- PCLK1 = 170 MHz,
- PCLK2 = 170 MHz,
- USB = 48 MHz,
- FDCAN kernel = 170 MHz,
- ADC1/ADC12 kernel = 42.5 MHz,
- PLL R output is enabled,
- there are no unresolved clock warnings.

Save the project.

# 10. Configure SPI1 for the ADS1262

## 10.1 Enable SPI1

Go to:

```text
Pinout & Configuration -> Connectivity -> SPI1
```

Under **Mode**, select:

```text
Full-Duplex Master
```

CubeMX may automatically assign SPI1 to PA5, PA6, and PA7. If it chooses another valid pin set:

1. click PA5 and select `SPI1_SCK`,
2. click PA6 and select `SPI1_MISO`,
3. click PA7 and select `SPI1_MOSI`,
4. lock all three pins.

## 10.2 Set SPI1 parameters

Open the **Parameter Settings** tab for SPI1 and use:

| Parameter | Setting | Explanation |
|---|---|---|
| Mode | Master | STM32 initiates every ADS1262 transaction |
| Direction | 2 Lines Full Duplex | Separate MOSI and MISO wires are used |
| Data Size | 8 Bits | ADS1262 commands and registers are byte-oriented |
| Clock Polarity, CPOL | Low | SCLK idles low |
| Clock Phase, CPHA | 2 Edge / Second Edge | Data is sampled on falling edges; this is SPI mode 1 |
| NSS | Software | PA4 is managed as a normal GPIO chip select |
| First Bit | MSB First | ADS1262 transmits most-significant bit first |
| TI Mode | Disabled | ADS1262 uses standard Motorola SPI framing |
| CRC Calculation | Disabled | ADS1262 uses its own optional interface/data integrity methods, not STM32 SPI CRC |
| NSS Pulse | Disabled, if shown | Chip select must remain controlled by the driver for complete commands |
| Baud-Rate Prescaler | 64 | Gives 2.65625 MHz from a 170 MHz SPI kernel clock |

The ADS1262 uses SPI mode 1. The initial 2.65625 MHz clock is intentionally conservative because the connection crosses the controller-to-sensor-board cable and operates beside motor electronics. It is still far faster than required for the expected sample rates. Increase it only after verifying SCLK, MOSI, MISO, and chip-select integrity with an oscilloscope.

## 10.3 Configure the ADS1262 support GPIOs

Assign:

- PA4 as `GPIO_Output`, label `ADS1262_CS_N`, initial level **High**.
- PC7 as `GPIO_EXTI7`, label `ADS1262_DRDY_N`, trigger **Falling Edge**.
- PC11 as `GPIO_Output`, label `ADS1262_RESET_N`, initial level **Low**.
- PD2 as `GPIO_Output`, label `ADS1262_START`, initial level **Low**.

#### Why CS starts high

A high chip-select deselects the ADC and prevents startup noise on SCLK/MOSI from being interpreted as a command.

#### Why RESET starts low

The ADS1262 RESET/PWDN input is active-low. Holding it low keeps the ADC reset/powered down while the digital and analog rails settle. Firmware later drives it high, waits the required startup time, and verifies the register defaults before configuration.

The PCB must define the reset state with an external resistor because the MCU pin is high impedance before GPIO initialization.

#### Why START starts low

The planned driver controls conversions with SPI commands. The ADS1262 documentation recommends keeping START low when command-based conversion control is used, avoiding contention between the pin and commands.

## 10.4 SPI GPIO electrical settings

CubeMX normally creates the alternate-function configuration automatically. Verify:

| Signal | GPIO type | Pull | Speed |
|---|---|---|---|
| PA5 SCLK | Alternate Function Push-Pull | No pull | Medium initially |
| PA6 MISO | Alternate Function Push-Pull/input path | No pull | Medium initially |
| PA7 MOSI | Alternate Function Push-Pull | No pull | Medium initially |
| PA4 CS_N | Output Push-Pull | No internal pull | Low or Medium |

The schematic should include small source-series resistors, approximately 22-47 ohms as tuning footprints, especially on SCLK. The ADS1262 datasheet recommends controlling ringing on serial-interface lines.

## 10.5 SPI interrupts and DMA

For Revision A:

- do not enable SPI DMA,
- do not enable the SPI1 global interrupt,
- use the ADS1262 DRDY interrupt to tell firmware when data is ready,
- perform short SPI transactions synchronously after DRDY.

This is simpler to debug. DMA can be added later if acquisition profiling shows a need.

- the MAX77960B charger/power-path IC or final selected equivalent,
- possible power-monitor devices.

= 14 / 17
= 82.35%

This is a reasonable initial sample point for a 500 kbit/s machine bus.

## 15.6 Handle CAN-transceiver standby in the schematic

Revision A does **not** spend an MCU GPIO on the TCAN1042-family standby input. PB9 is required for `TMC4_EN_N`, and PB4 is intentionally reserved.

On the controller schematic:

- hold the CAN transceiver in its normal operating state with the manufacturer-recommended resistor connection,
- include a test pad or jumper so standby can be forced during bench work if useful,
- ensure the transceiver cannot drive the bus before its supply is valid,
- do not connect the transceiver standby pin to PB9.

CubeMX therefore has no `CAN_STANDBY` GPIO in this baseline.

## 15.7 Enable the FDCAN interrupt

Enable **FDCAN2 interrupt line 0** in the NVIC settings. Use it for receive, transmit-complete, warning, error, and bus-off notifications selected later in firmware.

Leave interrupt line 1 disabled initially unless the firmware deliberately routes a second class of FDCAN events to it. One interrupt line is easier to understand during first bring-up and is adequate for this application.

The exact event masks are not selected in CubeMX; firmware enables them with the HAL FDCAN notification API.

## 15.8 External hardware requirement

The STM32 has an FDCAN protocol controller, not the differential physical layer. The PCB still needs:

- TCAN1042-family transceiver,
- CANH/CANL protection,
- selectable 120 ohm termination,
- optional common-mode choke footprint,
- screw terminal or selected connector.

# 17. Configure the four hardware step-pulse timers

## 17.1 Why timers generate STEP pulses

Do not generate step pulses with delays in the main loop. A timer peripheral produces consistent pulse timing independently of code execution jitter.

Each auger receives its own timer channel so firmware can configure a requested rate and start exactly one channel.

## 17.2 Common timer basis

All four step timers use:

```text
Timer kernel clock = 170 MHz
Prescaler = 169
Timer counter frequency = 170 MHz / (169 + 1) = 1 MHz
```

A 1 MHz timer tick equals 1 microsecond. This makes step pulse widths and periods easy to calculate.

## 17.3 Configure TIM2 for Auger 1

Go to:

```text
Timers -> TIM2
```

Set:

```text
Clock Source = Internal Clock
Channel 1 = PWM Generation CH1
```

Assign PA0 = `TIM2_CH1`, label `AUGER1_STEP`.

Under Parameter Settings:

| Parameter | Value |
|---|---:|
| Prescaler | 169 |
| Counter Mode | Up |
| Counter Period | 999 |
| Clock Division | Division 1 |
| Auto-Reload Preload | Enabled |
| PWM Mode | PWM mode 1 |
| Pulse | 0 |
| Output Polarity | High |
| Fast Mode | Disabled |

The placeholder period of 999 represents 1000 timer ticks or 1 ms, which would be 1 kHz if PWM were started. Pulse = 0 means no active pulse at startup.

Firmware later writes the period and compare value before starting PWM.

## 17.4 Configure TIM3 for Auger 2

Go to:

```text
Timers -> TIM3
```

Use the same common values.

Assign PC6 = `TIM3_CH1`, label `AUGER2_STEP`.

## 17.5 Configure TIM15 for Auger 3

Go to:

```text
Timers -> TIM15
```

Select Channel 1 PWM and assign PB14 = `TIM15_CH1`, label `AUGER3_STEP`.

Use the same prescaler, period, and pulse values.

TIM15 is an advanced/control timer on this MCU. Leave unused break/dead-time features disabled.

## 17.6 Configure TIM20 for Auger 4

Go to:

```text
Timers -> TIM20
```

Select Channel 1 PWM and assign PB2 = `TIM20_CH1`, label `AUGER4_STEP`.

Use the same common values.

TIM20 also exposes advanced motor-control options. For a STEP signal:

- Break input disabled,
- dead time = 0,
- complementary output disabled,
- automatic output disabled unless HAL requires the normal main-output behavior,
- off-state settings left at safe defaults.

## 17.7 Timer interrupts and DMA

Do not enable timer update interrupts or DMA for the baseline.

The timer hardware produces pulses after firmware starts PWM. Firmware can stop a move by stopping the channel or by counting pulses with a later interrupt/DMA strategy.

The final firmware implementation may add:

- update interrupt pulse counting,
- one-pulse mode,
- DMA-driven acceleration profiles,
- master/slave timer gating.

Those are firmware architecture decisions, not required to create the initial project.

## 17.8 STEP output GPIO speed

Use **Medium** speed initially. The required STEP frequency is low compared with the GPIO capability, and a slower edge reduces ringing and EMI. Increase only if oscilloscope measurements show inadequate edge timing at the TMC2209 module socket.

# 18. Configure auger direction and enable GPIOs

The four TMC2209 sockets have independent STEP, DIR, EN, and UART connections. Firmware will run only one auger at a time, but all four outputs must power up safely.

## 18.1 Direction outputs

Configure these as `GPIO_Output`:

| User label | Pin | Initial level | Why |
|---|---|---:|---|
| `AUGER1_DIR` | PA1 | Low | Gives a defined direction before any STEP pulse |
| `AUGER2_DIR` | PA10 | Low | Gives a defined direction before any STEP pulse |
| `AUGER3_DIR` | PB0 | Low | Gives a defined direction before any STEP pulse |
| `AUGER4_DIR` | PB3 | Low | Gives a defined direction before any STEP pulse |

For each:

```text
GPIO output level = Low
GPIO mode = Output Push Pull
GPIO Pull-up/Pull-down = No pull
Maximum output speed = Low
```

The logical meaning of low/high—clockwise or counterclockwise—depends on motor wiring and auger mechanics. Firmware should store a per-auger direction polarity rather than assuming all mechanisms are identical.

## 18.2 Active-low driver-enable outputs

Configure:

| User label | Pin | Initial level | Why |
|---|---|---:|---|
| `TMC1_EN_N` | PA3 | High | Driver 1 disabled |
| `TMC2_EN_N` | PA15 | High | Driver 2 disabled |
| `TMC3_EN_N` | PB1 | High | Driver 3 disabled |
| `TMC4_EN_N` | PB9 | High | Driver 4 disabled |

For each:

```text
GPIO output level = High
GPIO mode = Output Push Pull
GPIO Pull-up/Pull-down = No pull
Maximum output speed = Low
```

The `_N` suffix means the signal is active low: low enables the module; high disables it.

## 18.3 External pull-ups are mandatory

Place an external pull-up on every TMC `EN_N` line. Those resistors keep the modules disabled:

- before the MCU leaves reset,
- while firmware is being programmed,
- if the MCU supply fails,
- if a GPIO is accidentally reconfigured as an input.

CubeMX's initial output-high setting does not exist until `MX_GPIO_Init()` executes.

## 18.4 PB4 is not Auger 4 enable

Do not assign PB4 to `TMC4_EN_N`. PB4 remains `UCPD_PB4_RESERVED`; PB9 is the approved Auger 4 enable pin.

## 18.5 Direction-change rule for later firmware

The TMC2209 driver should be disabled or stopped before changing DIR, and DIR setup time must expire before the next STEP edge. CubeMX does not implement this sequence; the later motor-driver class must enforce it.

# 19. Configure safety, calibration, and diagnostic GPIOs

This section distinguishes **hardware safety** from **software status**. The MCU may observe the E-stop and may command motion permission, but it must not be the sole element that interrupts hazardous motion.

## 19.1 Global motion permission

Configure PB5:

```text
Mode = GPIO_Output
User label = GLOBAL_MOTION_ENABLE
Initial output level = Low
Output type = Push-Pull
Pull = No pull
Speed = Low
```

Interpretation:

- low = hardware motion gate disabled,
- high = firmware requests that the hardware motion gate permit operation.

Place an external pull-down so the motion gate remains disabled before firmware runs.

The physical E-stop must still be able to remove/inhibit TMC, calibration-actuator, and future robot-motion power independently of PB5.

## 19.2 E-stop status input

Configure PA8:

```text
Mode = GPIO_EXTI8
User label = ESTOP_OK
GPIO pull = No pull
External interrupt mode = Rising and Falling edge
```

Why both edges:

- falling edge reports that the safety chain opened,
- rising edge reports that the chain returned healthy,
- firmware can latch the fault and require an explicit reset even after the input rises again.

The external safety circuit must provide a defined 3.3 V-compatible logic level. The MCU interrupt is for logging/state control, not the primary stopping action.

## 19.3 Internal calibration/check-mass actuator

Configure PC4:

```text
Mode = GPIO_Output
User label = CAL_ACTUATOR_ENABLE
Initial output level = Low
Output type = Push-Pull
Pull = No pull
Speed = Low
```

PC4 is a logic command to an external transistor/H-bridge/actuator circuit. It must not directly drive a motor, solenoid, or relay coil.

Configure the two calibration-position inputs:

```text
PC5  = GPIO_Input, label CAL_HOME
PB11 = GPIO_Input, label CAL_END
Pull = No pull
```

Use explicit external pull resistors and sensor filtering in the schematic. The exact sensor polarity has not been frozen, so the baseline uses normal GPIO inputs and polls them. Convert them to EXTI later only after the switch/Hall/optical sensor circuit is finalized.

## 19.4 EMFC analog-servo clamp/reset

Configure PF0:

```text
Mode = GPIO_Output
User label = EMFC_SERVO_CLAMP
Initial output level = High
Output type = Push-Pull
Pull = No pull
Speed = Low
```

The planned TMUX1101 closes the integrator-clamp/reset path when its logic input is high. Therefore:

- high = analog servo integrator clamped/reset, safe startup,
- low = analog servo released for normal operation.

Place an external pull-up so the servo remains clamped while the MCU is reset or unpowered. Before releasing this line, firmware must verify ADC communication, optical plausibility, temperature status, and absence of OPA593 faults.

If the final analog schematic inverts this logic, change the signal name/description and CubeMX startup level before PCB release. Do not rely on a comment to correct an inverted safety state.

## 19.5 OPA593 active-low fault flags

The OPA593 Current Flag and Thermal Flag are open-drain outputs that assert low. Configure:

```text
PF1  = GPIO_EXTI1,  label OPA593_CURRENT_FLAG_N, trigger Falling edge
PC13 = GPIO_EXTI13, label OPA593_THERMAL_FLAG_N, trigger Falling edge
Pull = No pull in CubeMX
```

Place 5-10 kohm external pull-ups to 3.3 V, consistent with the OPA593 datasheet and interface design.

Interpretation:

- high = no fault,
- low = current-limit or overtemperature condition asserted.

Why falling-edge interrupt: the important transition is normal-high to alarm-low. Firmware must also read the pin levels during startup because a fault may already be asserted before interrupts are enabled.

## 19.6 Charger/power-manager interrupt

Configure PB15:

```text
Mode = GPIO_EXTI15
User label = CHARGER_INT_N
Trigger = Falling edge
Pull = No pull
```

Use the external pull-up and voltage level required by the final charger/power-path IC. Firmware later reads charger status registers over I2C; the interrupt only indicates that status changed.

## 19.7 USB VBUS presence

Configure PA9:

```text
Mode = GPIO_Input
User label = USB_VBUS_SENSE
Pull = No pull
```

The external divider/limiter must produce a legal MCU input voltage from 5 V USB VBUS. Poll this input during startup and normal operation. It controls when the self-powered USB device stack attaches to the host.

## 19.8 Reserved PB4

PB4 remains:

```text
Mode = GPIO_Input
User label = UCPD_PB4_RESERVED
Pull = No pull
```

Do not connect it to a motor enable, E-stop, actuator, or other critical circuit.

# 20. Configure ADC1 for battery and system-voltage monitoring

The STM32 internal ADC is used only for slow housekeeping measurements such as battery/system voltage. The external ADS1262 remains the precision mass-conversion ADC.

## 20.1 Enable ADC1 channel 9

Open:

```text
Pinout & Configuration -> Analog -> ADC1
```

In the ADC mode/channel list, enable:

```text
IN9 Single-ended
```

CubeMX should assign:

```text
PC3 = ADC1_IN9
```

Set the user label to:

```text
BATTERY_SENSE
```

If CubeMX assigns an internal channel or different pin, clear it and explicitly select PC3/ADC1_IN9.

## 20.2 ADC clock

Use:

```text
Clock Prescaler / Clock mode = Synchronous clock mode divided by 4
```

With HCLK at 170 MHz:

```text
ADC kernel clock = 42.5 MHz
```

Why: this remains comfortably inside the device's ADC clock limit and is far more than required for one occasional voltage sample.

## 20.3 Global ADC settings

Open **Parameter Settings** and set:

| CubeMX field | Value | Why |
|---|---|---|
| Resolution | 12 bits | Sufficient for battery/power diagnostics |
| Data Alignment | Right | Produces the normal unsigned integer representation |
| Scan Conversion Mode | Disabled | Only one regular channel is configured |
| Continuous Conversion Mode | Disabled | Firmware requests a reading when needed |
| Discontinuous Conversion Mode | Disabled | No scan sequence exists |
| Number of Conversions | 1 | One regular rank |
| External Trigger Conversion Source | Software Start | Firmware controls measurement time |
| External Trigger Conversion Edge | None | No external hardware trigger |
| DMA Continuous Requests | Disabled | One low-rate sample does not justify DMA |
| End Of Conversion Selection | End of single conversion | EOC indicates the one requested sample is ready |
| Overrun | Data overwritten or CubeMX default | Not consequential when one conversion is read immediately |
| Low Power Auto Wait | Disabled | Adds no useful behavior to this occasional sample |
| Oversampling | Disabled initially | Avoids hiding divider/ADC behavior during first bring-up |

If the CubeMX wording differs slightly, preserve the behavior: one software-triggered, noncontinuous, non-DMA, 12-bit conversion.

## 20.4 Configure regular rank 1

In the regular conversion table:

```text
Rank 1 channel = ADC1_IN9
Input mode = Single-ended
Sampling time = 640.5 ADC clock cycles
Offset number = None / disabled
Offset = 0
```

Use the longest available sample time if your CubeMX package presents a slightly different numeric label.

## 20.5 Why 640.5 cycles

The battery input should use a high-value resistor divider so it does not waste substantial energy continuously. A high source impedance takes longer to charge the ADC's internal sample-and-hold capacitor. The long sample window provides settling margin and reduces dependence on the exact divider resistance.

At 42.5 MHz, 640.5 cycles is only about 15 microseconds, which is insignificant for a battery reading made perhaps a few times per second or less.

The external schematic must still include:

- a divider ratio safe for the maximum possible pack/tool-battery/input voltage,
- an RC filter,
- suitable protection,
- resistor tolerances appropriate to the desired voltage accuracy.

## 20.6 Interrupt and DMA choices

Leave:

- ADC1 interrupt disabled,
- ADC DMA disabled.

Firmware can use this simple sequence:

1. start conversion,
2. poll with a bounded timeout,
3. read result,
4. stop/return.

This is not in a real-time path and should not complicate initial firmware.

## 20.7 Runtime ADC calibration

CubeMX initializes the ADC registers but does not replace the device's runtime self-calibration sequence. Firmware should run the HAL ADC calibration function during startup before accepting the first voltage reading.

After calibration, discard the first conversion or follow the procedure recommended by the current STM32G4 HAL/example package.

Enable CDC only. Firmware update support is a separate bootloader decision.

# 24. Configure NVIC interrupts deliberately

The NVIC controls which interrupt can preempt another. Lower numeric priority means higher urgency:

```text
Priority 0 is higher than priority 3.
Priority 3 is higher than priority 8.
```

Do not make every interrupt priority 0.

## 24.1 Keep the default priority grouping

Use the normal CubeMX/HAL priority grouping that provides preemption-priority bits and no meaningful subpriority for this initial project (`NVIC_PRIORITYGROUP_4` in typical generated code).

Enter **subpriority 0** for every interrupt unless the current CubeMX screen requires otherwise.

## 24.2 Understand shared EXTI vectors

GPIO EXTI lines are grouped:

- lines 5-9 share `EXTI9_5_IRQn`,
- lines 10-15 share `EXTI15_10_IRQn`.

For this pin map:

- PC7 ADS1262 DRDY and PA8 E-stop status share `EXTI9_5_IRQn`,
- PC13 OPA593 thermal flag and PB15 charger interrupt share `EXTI15_10_IRQn`,
- PF1 OPA593 current flag uses `EXTI1_IRQn` alone.

Signals sharing one IRQ cannot have different NVIC priorities. The callback/handler must inspect the GPIO pin that caused the event.

## 24.3 Initial priority table

Use these preemption priorities:

| Interrupt | Priority | Why |
|---|---:|---|
| `EXTI9_5_IRQn` | 3 | ADS1262 DRDY is time-sensitive; E-stop status shares the same vector, while physical stopping remains hardware-controlled |
| `EXTI1_IRQn` | 4 | OPA593 current-limit alarm |
| `EXTI15_10_IRQn` | 5 | OPA593 thermal alarm and charger status |
| `FDCAN2_IT0_IRQn` | 6 | Machine-network receive/error events |
| USB low-priority/global interrupt | 7 | Service/logging traffic must not preempt measurement capture excessively |
| USART1 global interrupt | 8 | Nextion receive |
| LPUART1 global interrupt | 8 | RS-485 receive |
| USART2, USART3, UART4, UART5 interrupts | 8 | TMC register traffic is low-rate |
| I2C3 error interrupt | 9 | Report bus errors |
| I2C3 event interrupt | 9 | Temperature/power traffic |

Leave priority 0-2 unused initially. This preserves room for a later truly critical interrupt without renumbering the entire system.

If CubeMX gives a warning about calling HAL functions from an interrupt whose priority is too high, review the HAL/RTOS rules. There is no RTOS in Revision A, but it is still good practice to keep ISRs short.

## 24.4 Enable only these baseline interrupts

Enable:

- EXTI line 1,
- EXTI lines 5-9,
- EXTI lines 10-15,
- USART1,
- USART2,
- USART3,
- UART4,
- UART5,
- LPUART1,
- I2C3 event/error,
- FDCAN2 interrupt line 0,
- USB global/low-priority interrupt generated by USB middleware.

Do not enable:

- SPI1 interrupt,
- ADC1 interrupt,
- timer update interrupts,
- DMA interrupts,
- FDCAN2 interrupt line 1,

for the baseline unless CubeMX middleware requires a specific exception.

## 24.5 ISR rules for later firmware

An interrupt should normally:

1. clear/acknowledge the hardware event through HAL or register access,
2. capture minimal data or set a flag,
3. return quickly.

Do not perform inside an ISR:

- long `HAL_Delay()` calls,
- Nextion page parsing,
- floating-point calibration fits,
- blocking I2C/SPI transactions with long timeouts,
- USB log formatting,
- a complete auger sequence.

For ADS1262 DRDY, either perform a tightly bounded short SPI read or wake a high-priority acquisition path. Measure ISR duration before deciding.

# 25. DMA decisions for Revision A

CubeMX offers DMA for many peripherals. DMA moves data without the CPU copying each byte.

DMA is deliberately limited in the first configuration:

| Peripheral | Initial DMA decision | Reason |
|---|---|---|
| ADS1262 SPI1 | Disabled | Short, infrequent transactions triggered by DRDY |
| Nextion USART1 | Disabled | Interrupt-driven framed protocol is simpler initially |
| TMC UARTs | Disabled | Configuration traffic is low bandwidth |
| RS-485 LPUART1 | Disabled | Protocol not yet frozen |
| I2C3 | Disabled | Temperature/power traffic is slow |
| Step timers | Disabled | Timer hardware generates pulses directly |
| ADC1 | Disabled | One occasional battery reading |

This is not a statement that DMA is undesirable. It is a deliberate bring-up choice that reduces hidden state and makes peripheral behavior easier to inspect.

Add DMA only after the corresponding driver interface and buffer ownership are defined.

## 26.3 Heap and stack reservations

Set:

```text
Minimum Heap Size  = 0x400   // 1024 bytes
Minimum Stack Size = 0x2000  // 8192 bytes
```

Why:

- USB middleware, nested HAL calls, interrupts, and diagnostic formatting can use meaningful stack.
- 8 KiB is a conservative starting reservation on an MCU with ample SRAM.
- The application architecture should avoid unbounded dynamic allocation, so 1 KiB heap is enough for early builds.
- Actual high-water measurement later determines whether stack must change.

These values are linker reservations, not runtime monitoring. A build succeeding does not prove stack usage is safe.

The preferred approach is still to put application code in separate user-created files.

# 27. Configure generated-function order and early startup behavior

Open:

```text
Project Manager -> Advanced Settings
```

Find the **Generated Function Calls** or initialization-order table. Field names vary slightly between CubeMX releases.

## 27.1 Desired generated initialization sequence

A practical order is:

```text
HAL_Init()
USER CODE SysInit: disable UCPD dead-battery pull-downs
SystemClock_Config()
MX_GPIO_Init()
MX_CRC_Init()
MX_ADC1_Init()
MX_I2C3_Init()
MX_SPI1_Init()
MX_USART1_UART_Init()
MX_USART2_UART_Init() / HalfDuplex_Init()
MX_USART3_UART_Init() / HalfDuplex_Init()
MX_UART4_Init() / HalfDuplex_Init()
MX_UART5_Init() / HalfDuplex_Init()
MX_LPUART1_UART_Init()
MX_TIM2_Init()
MX_TIM3_Init()
MX_TIM15_Init()
MX_TIM20_Init()
MX_FDCAN2_Init()
USB initialization deferred until VBUS is present
```

The exact half-duplex function names depend on the generated HAL template.

## 27.2 Why UCPD disable occurs before normal GPIO operation

The UCPD dead-battery pull-down can load PB6 when PA9 is high. Since PB6 is the Nextion TX pin and PA9 senses USB VBUS, disable the feature in the generated SysInit user section before `MX_GPIO_Init()` configures normal UART/GPIO operation.

Use:

```c
/* USER CODE BEGIN SysInit */
__HAL_RCC_PWR_CLK_ENABLE();
SET_BIT(PWR->CR3, PWR_CR3_UCPD1_DBDIS);
/* USER CODE END SysInit */
```

If the installed HAL provides a clearly named official convenience function, that function may replace the register write. Verify the exact function in the installed `stm32g4xx_hal_pwr_ex.h`; do not paste a function name from another STM32 family.

## 27.3 Why GPIO initialization is early

`MX_GPIO_Init()` establishes the configured runtime-safe states:

- TMC drivers disabled,
- global motion disabled,
- RS-485 receive mode,
- ADS1262 deselected and held reset,
- calibration actuator off,
- EMFC analog loop clamped.

Hardware pull resistors still provide the true reset-time states before this function runs.

## 27.4 Do not automatically start step timers

CubeMX should initialize timer registers but should not call:

```c
HAL_TIM_PWM_Start(...)
```

from startup code. Confirm no step timer starts automatically. Later firmware writes the period/pulse values and starts exactly one auger channel.

## 27.5 Defer USB device initialization

Generate the USB device function and middleware, but prevent an unconditional `MX_USB_Device_Init()` call if the **Do Not Generate Function Call** option is available.

Reason: this machine is self-powered. Firmware should attach the USB device only when `USB_VBUS_SENSE` indicates that a host is present. Otherwise the USB D+ pull-up can advertise a device onto an unpowered host connection.

If CubeMX cannot suppress the call in the GUI:

1. leave the function generated,
2. remove/defer the call only inside a preserved user-controlled startup path,
3. document the behavior,
4. verify after every regeneration.

## 27.6 Do not add application logic yet

Generate and build the untouched initialization project before adding drivers. This separates tool/configuration problems from application-code problems.

## 34.1 First build the pure generated C project

Do not convert or add C++ until the untouched generated project builds successfully. That gives you a known-good baseline.

## 34.2 Enable C++ support in CubeIDE

Right-click the project. Depending on the CubeIDE minor version, use a command similar to:

```text
Configure -> Convert to C++ Project
```

or create the first `.cpp` file and allow CubeIDE to add the C++ project nature/tool settings.

After conversion, rebuild before adding substantial code.

## 34.3 Keep generated files as C

Do not rename:

- `main.c`,
- `stm32g4xx_it.c`,
- `gpio.c`,
- `spi.c`,
- `usart.c`,
- `tim.c`,
- generated USB C files.

CubeMX expects those names and can regenerate them.

## 34.4 Add a C-to-C++ bridge

Create a user header, for example `Core/Inc/AppMain.h`:

```cpp
#pragma once

#ifdef __cplusplus
extern "C" {
#endif

void App_Init(void);
void App_RunOnce(void);

#ifdef __cplusplus
}
#endif
```

Create `Core/Src/AppMain.cpp`:

```cpp
#include "AppMain.h"

void App_Init(void)
{
    // Application objects and drivers are initialized later.
}

void App_RunOnce(void)
{
    // One nonblocking application/state-machine iteration.
}
```

In `main.c`, add the include and calls only inside CubeMX user sections:

```c
/* USER CODE BEGIN Includes */
#include "AppMain.h"
/* USER CODE END Includes */
```

```c
/* USER CODE BEGIN 2 */
App_Init();
/* USER CODE END 2 */
```

```c
/* USER CODE BEGIN 3 */
App_RunOnce();
/* USER CODE END 3 */
```

The `extern "C"` guard prevents C++ name mangling so the C-generated `main.c` can link to the C++ implementation.

## 34.5 C callbacks implemented in C++

HAL callbacks and USB callbacks may require C linkage. When implementing one in a `.cpp` file, use the exact prototype and `extern "C"` where needed, for example:

```cpp
extern "C" void HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin)
{
    // Dispatch quickly; do not perform long work here.
}
```

Do not define the same callback in both a C and C++ file.

## 34.6 Application-folder organization

A practical user-owned layout is:

```text
Core/Inc/app/
Core/Src/app/
Core/Inc/drivers/
Core/Src/drivers/
Core/Inc/measurement/
Core/Src/measurement/
Core/Inc/system/
Core/Src/system/
```

CubeMX generally leaves user-created files alone. Confirm includes/source folders remain in the CubeIDE build after regeneration.

## 34.7 Avoid dynamic allocation in real-time paths

Prefer:

- static objects,
- fixed-size buffers,
- bounded queues,
- explicit ownership.

Avoid repeated `new`, `delete`, uncontrolled `std::vector` growth, or heap use in ADC/motor/safety paths. The MCU has an FPU, so C++ is not the problem; nondeterministic memory behavior is.

# 37. Common first-time CubeMX mistakes

## Mistake 1: selecting a development board instead of the exact MCU

Symptom: pins and clocks are preconfigured for a Nucleo board.

Correction: create a new project using MCU Selector and select `STM32G491RET6`.

## Mistake 2: selecting the wrong STM32G491 package

Symptom: desired pins do not exist or physical pin numbers do not match Altium.

Correction: verify LQFP64 and exact `RET6` part.

## Mistake 3: allowing CubeMX to move locked schematic signals

Symptom: regenerated code uses a different UART or timer pin.

Correction: lock the physical pins after assignment and compare the pinout CSV after changes.

## Mistake 4: interpreting GPIO initial state as reset-time safety

Symptom: a motor driver briefly enables during reset.

Correction: add external pull resistors and hardware safety gating. CubeMX levels only apply after initialization.

## Mistake 5: enabling full JTAG

Symptom: PA15, PB3, or PB4 becomes unavailable.

Correction: SYS Debug must be `Serial Wire`, not JTAG.

## Mistake 6: using PB8 for a peripheral

Symptom: unpredictable boot behavior or inability to start application flash.

Correction: reserve PB8 for BOOT0 and use the external pull-down/test jumper.

## Mistake 7: configuring ADS1262 SPI as mode 0

Symptom: register reads are wrong or intermittent.

Correction: CPOL Low, CPHA Second Edge, which is SPI mode 1.

## Mistake 8: assuming USB CDC is firmware update support

Symptom: no update mechanism exists despite a USB connector.

Correction: use SWD now; design a bootloader/DFU mechanism later.

## Mistake 9: using USB VBUS to power the machine

Symptom: back-powering, host-port overload, or unintended partial power states.

Correction: VBUS is sense-only in this design. Main power comes from the machine power system.

## Mistake 10: enabling all watchdog features immediately

Symptom: the debugger constantly loses the target because the MCU resets.

Correction: enable IWDG only after the supervisor/refresher architecture exists.

## Mistake 11: setting every GPIO to Very High speed

Symptom: increased ringing and EMI near precision analog circuits.

Correction: use Low for static controls, Medium for step/SPI/UART starting points, and raise slew only after signal-integrity measurements.

## Mistake 12: forgetting I2C pull-ups

Symptom: SDA/SCL remain low or communications fail.

Correction: install physical external pull-up resistors; CubeMX does not create them.

## Mistake 13: treating CAN or RS-485 as built-in electrical interfaces

Symptom: MCU pins are connected directly to CANH/CANL or A/B.

Correction: the STM32 provides protocol peripherals; external transceivers are required.

## Mistake 14: generating code before installing the STM32G4 package

Symptom: missing Drivers/Middleware files or an unbuildable project.

Correction: install the STM32CubeG4 package and regenerate.

## Mistake 15: adding code outside USER CODE sections

Symptom: application code disappears after regenerating.

Correction: use separate files or protected sections.

## Mistake 16: using PB4 as the fourth motor enable

Symptom: unexpected reset-time behavior or UCPD/JTRST loading on a critical enable.

Correction: reserve PB4 and use PB9 for `TMC4_EN_N`.

## Mistake 17: forgetting the UCPD dead-battery disable

Symptom: PB6/Nextion TX is unexpectedly loaded, particularly when PA9 USB VBUS sense is high.

Correction: set `PWR_CR3.UCPD1_DBDIS` early in the SysInit user section and verify it in generated firmware.

## Mistake 18: expecting to edit the `.ioc` inside CubeIDE 2.x

Symptom: the `.ioc` opens as text or no graphical Device Configuration Tool appears.

Correction: edit and regenerate the `.ioc` in standalone STM32CubeMX, then refresh/import the project in CubeIDE.

# 38. Troubleshooting specific problems

## CubeMX does not show STM32G491RET6

1. update CubeMX,
2. install/update the STM32G4 package,
3. clear filters in MCU Selector,
4. search the full exact part number,
5. verify you are using CubeMX, not CubeMX2.

## A pin turns red after enabling a peripheral

A physical pin is already assigned. Click the red pin and inspect the conflicting functions. Do not let CubeMX choose an arbitrary alternative without checking this guide.

## The clock page is red

Possible causes:

- PLL input outside allowed range,
- PLL VCO outside allowed range,
- SYSCLK exceeds 170 MHz,
- USB does not have 48 MHz,
- a peripheral clock source is missing.

Return to the values in Section 8 and verify HSI16, PLLM=4, PLLN=85, PLLR=2.

## CubeMX refuses 170 MHz

Check that:

- the exact STM32G491 part is selected,
- the power/voltage scaling is allowed to enter boost mode,
- AHB/APB dividers are valid,
- no incompatible clock constraint is selected.

## FDCAN bit rate is not 500 kbit/s

Confirm:

- FDCAN kernel clock is 170 MHz,
- prescaler is 20,
- segment 1 is 13,
- segment 2 is 3,
- synchronization segment is the implicit one time quantum.

## Half-duplex TMC UART takes only one pin

That is expected. In Half-Duplex/Single-Wire mode the TX pin is bidirectional.

## CubeIDE cannot find the project

Import the project root folder containing `.project` and `.cproject`, not the `Core` subfolder.

## CubeIDE build fails because files are missing

Reopen CubeMX, verify the STM32CubeG4 package is installed, and regenerate with `Copy only the necessary library files`.

## ST-LINK cannot connect

Check:

- target 3.3 V present,
- common ground,
- SWDIO/SWCLK not swapped,
- NRST connected,
- BOOT0 low,
- debug mode set to Serial Wire,
- try Connect Under Reset,
- lower SWD frequency.

## Generated code enters Error_Handler during clock setup

Likely causes:

- supply voltage is unstable,
- MCU is the wrong part,
- generated clock configuration is inconsistent,
- flash/power setup was manually altered,
- hardware power pins or decoupling are incorrect.

Build and test the unmodified generated project before blaming later application code.
